# 边界：每一道挡什么、不挡什么

airlock 要解决的问题是「agent 手里的权限太大」。它的回答不是更聪明的 agent，而是让能写的东西离 agent 尽量远：调查的一侧拿不到写权限，写的一侧拿不到自由。下面每一道边界都写明它**挡住什么**和**挡不住什么**；挡不住的部分由后面的边界兜住，最后一道是凭证本身的权限。

## 1. 调查区只读

- **靠什么**：调查节点只挂只读身份；执行任何工具前先过守卫（`airlock/runner/guard.py` 的 readonly 规则 + `gate.py`）：`kubectl` 的变更动词、`helm` 安装升级、容器运行时变更、`systemctl`、`terraform apply`、`ssh/scp`、`git push`，以及 AWS 的「非读操作」（反向判定：不是 describe/get/list… 就拒）。MCP 工具默认全拒，逐个放行。写 `CLAUDE.md`、`.claude/`、`.airlock/` 这些会影响下一次运行或是本次记录的文件也被拒。
- **挡住**：模型手滑、被 webhook 里的文字带偏之后想直接动手。
- **挡不住**：守卫是对命令字符串的正则，`V=delete; kubectl $V pod x` 这类会漏过。所以真正的边界是**只读凭证**——守卫只是把意外变成一条清楚的拒绝记录。凭证如果给宽了，守卫兜不住；姿态自检（`AIRLOCK_POSTURE_FILE`）就是为了在启动时把「宣称只读」变成「测过只读」，测不过就拒绝接活。

### 1b. 不在容器里时：限制模式

- **靠什么**：调查节点跑在本机（demo、本地试用）时设 `AIRLOCK_CONFINE=1`（`airlock/runner/sandbox.py`）：只提供 Bash、Read、Write、Edit、Glob、Grep、TodoWrite 和会诊工具，其他工具一律拒；文件工具的路径必须在工作目录里（跟随符号链接判断）；shell 只允许一小组只读命令（cat、grep、ls、find 不带动作……），不许变量和命令替换、重定向、子 shell、后台任务，每个参数都按路径检查。
- **挡住**：真模型在笔记本上顺手读到 `~/.aws`、`~/.ssh`、别的项目的 `.env`，然后把内容当工具输出发给模型网关。2026-09-23 用真 CLI 验证过：工作目录外的诱饵文件用 Bash 和 Read 都读不到。
- **挡不住**：它是命令字符串层面的白名单，不是内核沙箱；工作目录里放了什么，模型就能读到什么。另外 CLI 自己的系统提示会带上工作目录路径和它是不是 git 仓库、平台、日期，所以工作目录要放在任何仓库之外。

### 1c. MCP 服务器和 skills

- **靠什么**：MCP 服务器只来自 `AIRLOCK_MCP_CONFIG` 这一份文件（strict），每次运行重新读；文件放在调查员写不了的地方，否则节点拒绝启动；MCP 工具默认全拒，逐个放行（`AIRLOCK_MCP_ALLOWED`）。skills 从工作目录的 `.claude/skills` 加载，打开后 CLI 也读工作目录的 `.claude/settings.json` 和 `CLAUDE.md`；这些路径都在守卫的保护名单里，调查员改不了自己的说明书。
- **挡住**：模型调用没放行的工具，比如同一个服务器上的"重启"工具。2026-09-23 用真 CLI 验证过：被拒的调用根本没到服务器；也挡住调查员往配置里加服务器、或者改写 skill 让下一次运行照做。
- **挡不住**：MCP 服务器进程和调查员同用户、同容器，服务器的凭证（环境变量、配置里的 token）调查员也读得到，然后可以绕开工具名单直接调 API。所以调查员的 MCP 服务器只能配只读凭证，和它的 shell 一样；服务只发能写的凭证时，见 1d。

### 1d. 凭证能写的 MCP 服务器：网关

- **靠什么**：服务只发一种能读也能写的 key 时，服务器放到 `airlock/mcpgate.py` 后面。
  - 凭证只在网关的容器里，调查员拿的是一个只在网关有效的 token，每个调查画像一个，各自只能用配给它的服务器。
  - `tools/call` 只转发为这台服务器列出的工具，`tools/list` 里其余工具被删掉；协议自己的列举、读取请求照常转发，此外一律在网关回错误。
  - 每次工具调用，放行的和被拒的，都记进网关自己的哈希链记录。
  - 调查员在 `tools` 网络上，网关出网的 `outside` 网络它不在，服务器的域名它连解析都解析不到；出网代理的白名单里也没有这台服务器。
- **挡住**：调查员读到那把能写的 key，然后绕开工具名单直接调服务器的 API（比如确认告警、写入事件）。2026-09-23 在云服务器的部署上验证过：
  - 调查员容器里找不到那把 key；
  - 直连服务器解析不到域名，经代理返回 403；
  - 不在名单上的调用被网关拒掉，没有到达服务器。
- **挡不住**：名单里的"读"工具本身有副作用（比如按次计费的检索）；读到的内容照样会作为工具输出发给模型网关。网关 token 本身也是一份凭证，只是它能做的就是名单里那些读。名单要按服务器的源码核对，不能只看工具的名字或者它自称的 `readOnlyHint`。

### 1e. 记忆和评价

- **靠什么**：
  - 调查员的记忆文件在控制面的数据目录里，调查员只能只读挂载；
  - 只有你在控制台点「接受」，这一条才会被写进去；
  - 报告里的 `MEMORY-SUGGESTION` 行只进待审队列，每条都记账；
  - 已经不归这个调查员的工作项，它再报上来的内容一律拒收，里面的建议也不会进队列；
  - 评价和报表只读，不参与任何决定。
- **挡住**：一条被注入的消息让调查员“记住”某个说法，从此影响之后的每一次调查。
- **挡不住**：你接受了一条写得很像样、其实是错的“事实”。所以记忆的开头写明了“接受时为真，方案依赖它之前再核实一次”，每一条也都标了来源工作项。

### 1f. 节点自己的状态

- **靠什么**：调查节点的会话和记录放在 `AIRLOCK_STATE_DIR`，守卫拒绝任何工具读写它（文件工具的路径、shell 命令里出现它的路径都算）。
- **挡住**：一个工作项的调查翻到这个节点经手的其他工作项的记录。2026-09-23 真模型跑 demo 时，调查员就顺手读了自己的记录目录，这条规则是因此加的。这不是凭证边界（记录本来就是同一个调查员写的），是让"不同告警不共用会话"在文件层面也成立。
- **挡不住**：状态目录在工作目录里时，递归搜索仍可能扫到它的文件名，所以部署时把它放到工作目录外（`deploy/compose.yml` 里是单独的 `/state` 卷）。

## 2. 调查员之间只经控制面

- **靠什么**：调查节点没有彼此的地址。会诊由控制面转发：只有工作项的主人能问、只能问 `may_consult` 里的画像、只问一层（被问的一方没有会诊工具，控制面也不接受非主人的会诊）、每个工作项有次数上限，问题和答复都做凭证形状脱敏并记账。
- **挡住**：一个画像借另一个画像的权限绕圈子；会诊无限递归；把别的画像看到的密钥原样传过来。
- **挡不住**：答复里语义上的敏感信息（不是凭证形状的）会传过去——会诊本来就是为了传信息。

## 3. 计划的形状和自动校验

- **靠什么**：计划是固定 schema（`airlock/plans.py`）。每步指定工作画像和目标；命令是 argv 不是 shell 字符串，拼起来必须**完整匹配**该画像白名单里的一条正则；再过一遍灾难底线（`rm -rf`、格式化磁盘、整个命名空间删除、容器运行时……）；每个用到的工作画像要声明权限且不能超过上限，没用到的不许声明。
- **挡住**：调查员写出白名单之外的命令、一个画像越权做另一个画像的事、「顺手」多要权限。
- **挡不住**：白名单写宽了（比如 `.*`）就等于没有；`allowed_permissions` 只是给你看的标签，真正执行权限的是凭证。

## 4. 你的一次批准

- **靠什么**：批准必须带上你读到的版本号和 plan hash，任何一个字变了都是新版本、要重新批准；批准只能用一次，默认 24 小时过期；网页会话是签名 cookie（HttpOnly、SameSite=Strict、https 下 Secure），每个改变状态的表单带会话绑定的 CSRF token；登录失败有节流并记账。适配器只能替映射过的平台用户说话。
- **挡住**：批准了 A 执行了 B；旧批准被重放；别的网站替你点按钮；群里别人替你批准。
- **挡不住**：你批准了一份写得很像样的坏计划。计划页因此把步骤、目标、精确命令、权限、回滚、验证和相对上一版的差异全摊开；风险高的计划值得多看一眼。还有：**控制面本身被攻破**时它可以伪造批准——现在启动器信任控制面的签名。下一步是让批准由只在你设备上的密钥签名（WebAuthn），启动器验它，而不是信任控制面。

### 4b. 沙箱规则：不用你点的那一种批准

- **靠什么**：工作画像写 `approval: sandbox` 以后，计划的每一步都在这类画像上时，由沙箱规则批准，不等你点。
  - 它仍然是一次批准：绑定版本号和 hash，只能用一次，会过期，账本里的批准人记为 `policy:sandbox`。
  - 同一版规则只批一次。方案原样再发一遍，要你来批。
  - 每个画像每 24 小时最多批 `sandbox_runs_per_day` 次，默认 10。用完以后这一版等你批准，卡片上会写明。
  - 配置加载时检查画像的形状：
    - 必须有 `repos`（每次一份没有 remote 的新克隆），不能有固定工作目录；
    - 环境变量只许代理和语言区域，代理地址里不许带账号密码；
    - 网络不能是 `host` 或 `bridge`。
  - 启动器按**它自己那份**画像再查一遍：
    - 这个画像确实是 sandbox；
    - 运行时是容器（本地运行时一律拒）；
    - 凭证目录里只有 `engine.env`，里面也只有模型设置。启动器容器只读挂着 `${AIRLOCK_ROOT}/creds`，沙箱画像的凭证目录要放在它下面；读不到就一律拒。2026-09-24 第一次真跑时就是这样被拒的：当时启动器没挂这个目录；
    - 网络是 `none` 或 internal 网络，启动时用 `docker network inspect` 查，结果在 `/healthz` 的 `sandbox_networks` 里；
    - 这个画像 24 小时内按规则跑的次数没有超，数的是启动器自己的记录。
  - 调查员的提示词里写明哪些是沙箱画像、能改哪些仓库，以及计划里只要有一步不在沙箱画像上就要等你批准。
- **挡住**：
  - 用规则跑能碰真实系统的计划：只要有一步在别的画像上，整份计划都要你批准。
  - 配置两边不一致：控制面以为是沙箱画像，启动器那份不是，启动器就拒绝。
  - 沙箱画像多拿一把钥匙：凭证目录里多一个文件，或者 `engine.env` 里多一个不是模型设置的变量，都会被拒。
  - 被注入的调查员拿规则反复烧钱：每个画像每天有次数上限，同一版只批一次。
- **挡不住**：
  - 镜像里本来就有的东西。镜像是你选的，启动器不检查里面装了什么。
  - 同一个 internal 网络上的其他容器。沙箱 worker 能连到它们，所以那个网络上的服务都要各自验凭证：调查员的接口要签名，网关要 token。
  - 代码发给模型网关。worker 读到什么就发给模型，和调查员读代码时一样；出网名单里能接收任意内容的主机，也能被用来把代码发出去。
  - diff 本身写得不对。规则批准的是"在沙箱里跑"，不是"这个改动对"；diff 要你审，用不用由你决定。
  - 控制面被攻破。它能伪造你的批准，也就能伪造规则的批准，见上一节最后。

## 5. 启动器复核

- **靠什么**：启动器是唯一能起工作容器的组件，只接受启动器密钥签名的请求（只有控制面有），并且自己重算 plan hash、查过期、查是否用过（重启后仍记得）、用**它自己那份**工作画像配置重新校验，同一目标同时只允许一份计划。沙箱规则的批准还要过 4b 列的那几项。拒绝也记录在 `runs/refusals.jsonl`。
- **挡住**：控制面被说服了去执行一份白名单外的计划；同一批准执行两次；两份计划同时改同一个目标。
- **挡不住**：控制面密钥和启动器密钥同时泄露。部署时把启动器放在只有控制面能连的网络上（`deploy/compose.yml` 的 `launch` 网络），调查员根本连不到它。

## 6. 工作容器

2026-09-23 在真 Docker 上实测过（`tests/test_docker.py`），每一条都由容器里的姿态自检自己证明并记进执行记录。

- **靠什么**：一组步骤一个新容器：`--rm`、只读根文件系统、`noexec` 的小 tmpfs、`--cap-drop ALL`、`no-new-privileges`、进程数和内存上限、默认 `--network none`、以启动器自己的 uid 运行（启动器是 root 时退到 65534，容器里永远不是 root，除非画像显式配置 `user`）；只挂该画像自己的凭证目录且只读。第一步之前先跑姿态自检。命令不经 shell、有超时，第一步失败即停。
- **挡住**：凭证在任务之间残留；一个画像的容器里出现别的画像的钥匙；进程逃出预算；任务之间互相污染。
- **挡不住**：凭证本身能做的事。一个能删整个数据库的凭证，在白名单允许的命令里也可能删掉它——所以专用身份的权限要收到白名单那几条命令刚好够用。
- **收窄的例子**：主机维护画像用的 SSH key，在主机的 `authorized_keys` 里用 `command=` 绑到 `deploy/host/airlock-maint`，禁掉端口转发和 pty。worker 发来什么都只是这个脚本的一个参数，脚本只认三条子命令。姿态自检让它跑一条别的命令（`whoami`），拒绝了才开始执行。主机那边的日志另记一份，每次调用都在，被拒的也在。task 模式（容器里跑一个 agent）只有灾难底线守卫，适合有工作区、权限很窄的画像（比如只能推分支不能合并的仓库令牌）。

### 6b. 改代码的工作画像

- **靠什么**：
  - 画像用 `repos` 列出能改的仓库，计划的目标必须是其中之一（`repo:<名字>`），控制面和启动器各校验一次。
  - 每次运行，启动器在容器外克隆一份，删掉 remote，只把这份克隆挂进容器。
  - 跑完以后，启动器拿镜像里起点提交的文件和工作区当前的文件比，算出 diff，连同 hash 记进运行目录和账本。
  - 工作区只当普通文件读：不在里面跑 git，跳过 `.git`，符号链接只记指向不读内容，管道、设备这类特殊文件跳过。
- **挡住**：
  - 改动绕过镜像、推到别处：没有 remote，容器里也没有推送凭证。
  - 这次运行留下的东西影响下一次运行：每次都是新克隆。
  - worker 谎报改了什么：diff 是启动器算的。
  - worker 借启动器执行自己的代码：比如在 `.git/config` 里写 `core.fsmonitor` 或 filter 驱动，等启动器跑 git 时触发。测试里验证过，标记文件没有被创建。
  - worker 借启动器读容器外的文件：符号链接不跟随，测试里验证过。
- **挡不住**：
  - 改动本身写得不对：diff 摊在执行结果里，要人来看。
  - worker 在运行期间用它拿到的东西做别的事：模型的 key 在它自己的凭证目录里，它读得到；能发到哪里，由出网代理的名单决定。
  - 文件权限位不在比较范围内。

## 7. 记录

- **靠什么**：控制面账本和每次执行的记录都是只追加、每条带前一条的哈希；执行器把记录实时写到 stdout，启动器在容器外落盘并校验链、核对容器最后报告的链头与它流出来的是否一致，对不上就判这组失败。输出按凭证形状脱敏后保存，同时保留原始输出的哈希。每次执行结束，账本链头作为 `ledger.checkpoint` 发给订阅方另存。AWS 调用带 `airlock-<批准编号>` 的 User-Agent。
- **挡住**：事后改一条记录、删一条记录而不被发现（只要链头在别处有一份）；容器里的进程改自己的执行记录（记录不在容器里）。
- **挡不住**：有写权限的人重建一条自洽的新链——所以链头必须在别处存一份：`python -m airlock.witness serve` 就是那个"别处"，放在另一台机器、另一个账号下，`verify` 用它存的链头核对账本。task 模式下容器里的 agent 理论上能往 stdout 注入伪造行（它和执行器同一个用户），链校验能发现断链但不能证明缺了什么；需要强证据的目标用 commands 模式。与目标系统原生审计的对账：`python -m airlock.reconcile` 把 CloudTrail / k8s 审计里专用身份的每一次调用对到执行窗口，对不上就报。它只读导出的文件，拉日志要部署来安排。

## 7b. 核心之外的部件

- **盯守**（`airlock/extras/watch`）：
  - **靠什么**：
    - 判断的模型没有任何内置工具，只有配置里点名的 MCP 工具（聊天的只读工具，经网关）；
    - 它读不到状态文件和进程环境，也发不出任何东西；
    - 投递由盯守进程签名；每条信号都要对上这一轮扫描实际给出的会话或工单，对不上就丢掉；
    - 游标在这一轮判断成功之后才推进，模型挂了下一跳会重读同样的消息。
  - **挡住**：
    - agent 拿签名密钥自己发信号；
    - 报一个这一轮根本没给它的会话；
    - 模型故障时悄悄吞掉一轮消息。
  - **挡不住**：它读的是别人写的字，被提示注入带偏以后，可能把一条假请求报成 task。那条 task 走的仍是只读调查，要动任何东西还得你在控制台批准。一条 note 也可能把误导性的文字发进你的群。
- **飞书适配器**（`airlock/extras/feishu`）：
  - **靠什么**：
    - 两个入口各自验签：出口通知一个密钥，盯守的 note 一个密钥；
    - 同一条通知只发一次；
    - 卡片里的 lark_md 全部转义；
    - 只认 `people` 里的人，airlock 端按适配器的 `identities` 再核对一次；
    - 卡片没有批准按钮。
  - **挡住**：
    - 伪造的通知进群；
    - 标题里的 `<at id=all>` 把全员 @ 出来；
    - 群里别人冒充你留言或开工作项；
    - 聊天账号变成第二把批准钥匙。
  - **挡不住**：拿到你聊天账号的人能以你的名义留言、开工作项。批准仍然只能在控制台。
- **自检**（`airlock/extras/selfcheck`）：告警走它自己的机器人 webhook，飞书适配器挂了也报得出来。盯守不跳、上一轮失败、有信号没送到，都会告警。
- **代码镜像**（`airlock/extras/mirrors`）：token 只读，经 credential helper 从环境变量读，不出现在任何命令行上，报错里会把它替换掉。镜像每次都强制对齐远端，谁手改了都会被覆盖。

## 8. 出网

- **靠什么**：调查容器所在网络的唯一出口是出网代理（`airlock/egress/proxy.py`），只放行名单里的主机名和端口，拒绝都记 WARNING；守卫也拒绝 `unset HTTPS_PROXY`、`curl --noproxy` 这类绕行。
- **另一条路**：用 MCP 网关的调查员还能连到网关（`tools` 网络），网关自己直接出网。但它只连配置里写死的服务器地址，调查员决定不了它去哪。
- **挡住**：意外或投机地把数据发到名单外的地方；绕开代理的常见写法。
- **挡不住**：名单里本身能接收任意内容的主机（比如模型网关接受 POST）；自己写程序开 socket 不读代理变量——网络隔离（internal 网络）才是这里真正的边界。`scripts/compose_smoke.py` 从调查员容器里验证过：连启动器解析不到、直连外网不通、经代理只有名单里的主机能出去。
- **踩过的坑**：代理原来用带缓冲的方式读请求头，客户端不等 200 就发 TLS 握手时，握手包会被吞掉、连接一直挂着；已改成不缓冲读（有测试）。hookstack 的出网代理是同一份代码，同样有这个问题。
