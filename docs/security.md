# 边界：每一道挡什么、不挡什么

airlock 要解决的问题是「agent 手里的权限太大」。它的回答不是更聪明的 agent，而是让能写的东西离 agent 尽量远：调查的一侧拿不到写权限，写的一侧拿不到自由。下面每一道边界都写明它**挡住什么**和**挡不住什么**；挡不住的部分由后面的边界兜住，最后一道是凭证本身的权限。

## 1. 调查区只读

- **靠什么**：调查节点只挂只读身份；执行任何工具前先过守卫（`airlock/runner/guard.py` 的 readonly 规则 + `gate.py`）：`kubectl` 的变更动词、`helm` 安装升级、容器运行时变更、`systemctl`、`terraform apply`、`ssh/scp`、`git push`，以及 AWS 的「非读操作」（反向判定：不是 describe/get/list… 就拒）。MCP 工具默认全拒，逐个放行。写 `CLAUDE.md`、`.claude/`、`.airlock/` 这些会影响下一次运行或是本次记录的文件也被拒。
- **挡住**：模型手滑、被 webhook 里的文字带偏之后想直接动手。
- **挡不住**：守卫是对命令字符串的正则，`V=delete; kubectl $V pod x` 这类会漏过。所以真正的边界是**只读凭证**——守卫只是把意外变成一条清楚的拒绝记录。凭证如果给宽了，守卫兜不住；姿态自检（`AIRLOCK_POSTURE_FILE`）就是为了在启动时把「宣称只读」变成「测过只读」，测不过就拒绝接活。

## 2. 调查员之间只经控制面

- **靠什么**：调查节点没有彼此的地址。会诊由控制面转发：只有工作项的主人能问、只能问 `may_consult` 里的画像、只问一层（被问的一方没有会诊工具，控制面也不接受非主人的会诊）、每个工作项有次数上限，问题和答复都做凭证形状脱敏并记账。
- **挡住**：一个画像借另一个画像的权限绕圈子；会诊无限递归；把别的画像看到的密钥原样传过来。
- **挡不住**：答复里语义上的敏感信息（不是凭证形状的）会传过去——会诊本来就是为了传信息。

## 3. 计划的形状和自动校验

- **靠什么**：计划是固定 schema（`airlock/plans.py`）。每步指定工作画像和目标；命令是 argv 不是 shell 字符串，拼起来必须**完整匹配**该画像白名单里的一条正则；再过一遍灾难底线（`rm -rf`、格式化磁盘、整个命名空间删除、容器运行时……）；每个用到的工作画像要声明权限且不能超过上限，没用到的不许声明。
- **挡住**：调查员写出白名单之外的命令、一个画像越权做另一个画像的事、「顺手」多要权限。
- **挡不住**：白名单写宽了（比如 `.*`）就等于没有；`allowed_permissions` 只是给你看的标签，真正执行权限的是凭证。

## 4. 你的一次批准

- **靠什么**：批准必须带上你读到的版本号和 plan hash，任何一个字变了都是新版本、要重新批准；批准只能用一次，默认 24 小时过期；网页会话是签名 cookie（HttpOnly、SameSite=Strict、https 下 Secure），每个改变状态的表单带会话绑定的 CSRF token；登录失败有节流并记账。适配器只能替映射过的平台用户说话。
- **挡住**：批准了 A 执行了 B；旧批准被重放；别的网站替你点按钮；群里别人替你批准。
- **挡不住**：你批准了一份写得很像样的坏计划。计划页因此把步骤、目标、精确命令、权限、回滚、验证和相对上一版的差异全摊开；风险高的计划值得多看一眼。还有：**控制面本身被攻破**时它可以伪造批准——现在启动器信任控制面的签名。下一步是让批准由只在你设备上的密钥签名（WebAuthn），启动器验它，而不是信任控制面。

## 5. 启动器复核

- **靠什么**：启动器是唯一能起工作容器的组件，只接受启动器密钥签名的请求（只有控制面有），并且自己重算 plan hash、查过期、查是否用过（重启后仍记得）、用**它自己那份**工作画像配置重新校验，同一目标同时只允许一份计划。拒绝也记录在 `runs/refusals.jsonl`。
- **挡住**：控制面被说服了去执行一份白名单外的计划；同一批准执行两次；两份计划同时改同一个目标。
- **挡不住**：控制面密钥和启动器密钥同时泄露。部署时把启动器放在只有控制面能连的网络上（`deploy/compose.yml` 的 `launch` 网络），调查员根本连不到它。

## 6. 工作容器

- **靠什么**：一组步骤一个新容器：`--rm`、只读根文件系统、`noexec` 的小 tmpfs、`--cap-drop ALL`、`no-new-privileges`、进程数和内存上限、默认 `--network none`、以启动器自己的 uid 运行（启动器是 root 时退到 65534，容器里永远不是 root，除非画像显式配置 `user`）；只挂该画像自己的凭证目录且只读。第一步之前先跑姿态自检。命令不经 shell、有超时，第一步失败即停。
- **挡住**：凭证在任务之间残留；一个画像的容器里出现别的画像的钥匙；进程逃出预算；任务之间互相污染。
- **挡不住**：凭证本身能做的事。一个能删整个数据库的凭证，在白名单允许的命令里也可能删掉它——所以专用身份的权限要收到白名单那几条命令刚好够用。task 模式（容器里跑一个 agent）只有灾难底线守卫，适合有工作区、权限很窄的画像（比如只能推分支不能合并的仓库令牌）。

## 7. 记录

- **靠什么**：控制面账本和每次执行的记录都是只追加、每条带前一条的哈希；执行器把记录实时写到 stdout，启动器在容器外落盘并校验链、核对容器最后报告的链头与它流出来的是否一致，对不上就判这组失败。输出按凭证形状脱敏后保存，同时保留原始输出的哈希。每次执行结束，账本链头作为 `ledger.checkpoint` 发给订阅方另存。AWS 调用带 `airlock-<批准编号>` 的 User-Agent。
- **挡住**：事后改一条记录、删一条记录而不被发现（只要链头在别处有一份）；容器里的进程改自己的执行记录（记录不在容器里）。
- **挡不住**：有写权限的人重建一条自洽的新链——所以链头必须在别处存一份。task 模式下容器里的 agent 理论上能往 stdout 注入伪造行（它和执行器同一个用户），链校验能发现断链但不能证明缺了什么；需要强证据的目标用 commands 模式。与目标系统原生审计（CloudTrail、k8s audit）的自动对账还没做。

## 8. 出网

- **靠什么**：调查容器所在网络的唯一出口是出网代理（`airlock/egress/proxy.py`），只放行名单里的主机名和端口，拒绝都记 WARNING；守卫也拒绝 `unset HTTPS_PROXY`、`curl --noproxy` 这类绕行。
- **挡住**：意外或投机地把数据发到名单外的地方；绕开代理的常见写法。
- **挡不住**：名单里本身能接收任意内容的主机（比如模型网关接受 POST）；自己写程序开 socket 不读代理变量——网络隔离（internal 网络）才是这里真正的边界。
