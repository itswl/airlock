# airlock

**调查只读；要改东西，先出一份计划，你批准的那一版才会在隔离容器里、用专用凭证执行，每一步都有记录。**

你的权限太高了，所以把「看」和「动」拆开：

- **调查**只拿只读（或者你指定的）凭证，常驻、可以并行好几个画像，谁也碰不到写权限。
- **操作**可以挂高风险的永久凭证，但它不常驻、没有聊天入口：只在你批准一份具体计划之后才被拉起来，一组步骤一个容器，做完就删。
- **你只在一个地方必须点**：把调查结论交给工作节点的那一下。之前可以在计划下留言商量，每次修订都是新版本，批准只对你读到的那一版（版本号 + hash）有效。
- **全程留痕**：控制面账本和每次执行的记录都是只追加、带哈希链的；执行记录在启动器这边，不在被执行的容器里。

不依赖飞书：网页和 webhook 是主干，飞书、Slack、邮件都只是订阅签名通知、回传留言和批准的适配器。

骨架是写死在代码里的：进管道、分给一个调查画像、出计划、你批准、启动器执行、记账。可以配的是两端和画像——有哪些来源、每个来源哪些事件算工作、分给谁、有哪些调查画像和工作画像、每个工作画像能跑哪些命令、最多能有哪些权限。没有 hookstack 那种任意拼接的管道。

## 一件事怎么走完

1. **进管道**：webhook 按来源各自验签（GitHub `X-Hub-Signature-256`、Jira `X-Hub-Signature`、本系统的时间戳 HMAC、Bearer），按 `accept` 规则筛选，同一个 key 在窗口内并入已开的工作项，然后按 `routes` 分给一个调查画像。每条进来的事件，包括被拒、被过滤的，都能在「接入事件」页查到原因。
2. **调查**：调查节点在只读守卫下工作（`kubectl delete`、`aws … put-*`、`helm upgrade` 之类在执行前就被拒并记录）。需要别的画像的视角时，经控制面问一次（只能问配置允许的对象，只问一层，有次数上限，答复脱敏）。
3. **出计划**：需要改动时，报告末尾附一个 ```` ```plan ```` JSON：每一步指定工作画像和目标，命令是精确 argv，列出每个工作画像需要的权限，写清回滚和验证。控制面立即校验：画像存在、模式允许、命令完整匹配白名单、不触碰灾难底线、权限不超上限；不合格的自动打回给调查员修，修不好才让你看到。不需要改动就只交报告。
4. **你决定**：网页上看步骤、目标、命令、权限、回滚、验证，以及相对上一版改了什么。留言 → 调查员按你的话修订 → 新版本。满意就点「批准 vN 并执行」。批准 24 小时内有效（可配），只能用一次；启动前可以撤回，执行中可以急停。
5. **启动器再查一遍**：自己重算 hash、查时效、查是否用过、按**它自己那份**工作画像重新校验（控制面被说服了也没用），同一目标同时只允许一份计划在动。
6. **执行**：连续的同画像步骤一组，一组一个容器（`--rm --read-only --cap-drop ALL --security-opt no-new-privileges`，默认无网络，只挂该画像的凭证目录且只读）。每组先跑姿态自检（比如「我是不是那个专用身份」「我是不是删不了命名空间」），不对就一步都不跑。每条命令无 shell、带超时、输出脱敏后留档并记哈希；第一步失败即停，后面的记为跳过。
7. **记录**：执行器把每一行记录实时写到 stdout，启动器在容器外落盘并校验哈希链；每一步的结果回到控制面账本；执行结束把账本链头作为 `ledger.checkpoint` 发给订阅方另存。AWS 调用会带上 `airlock-<批准编号>` 的 User-Agent，CloudTrail 里能对上。

## 快速体验（不需要模型、不需要 Docker）

```bash
python3 -m venv .venv && .venv/bin/pip install -e '.[dev]'
.venv/bin/python scripts/demo.py
```

它在 127.0.0.1 上起控制台（18080）、两个调查员（stub 引擎，infra 会请教 code）和启动器（local runtime，普通子进程，记录里标 `isolation: none`），并送进一条演示告警。打开打印出来的链接（密码 `airlock-demo-password`）：看计划 → 留言「先 drain」→ 看 v2 和差异 → 批准 → 看执行记录和账本。所有数据写在本仓库的 `data/demo/<时间>/` 下，命令全是 `echo`。

`scripts/demo.py --smoke` 用随机端口把上面整个流程自动走一遍然后退出。

### 换成真模型

```bash
pip install -e '.[claude]'          # Claude Agent SDK，自带 Claude Code CLI
export ANTHROPIC_BASE_URL=…  ANTHROPIC_AUTH_TOKEN=…  AIRLOCK_MODEL=…   # 任何 Anthropic 兼容网关
.venv/bin/python scripts/demo.py --engine claude
```

两个调查员换成真的 Claude 引擎，读的是一套编造的故障证据（日志、指标、runbook；部署历史只在 code 那边，infra 要去会诊）。它们在本机跑，所以是**受限模式**（`AIRLOCK_CONFINE=1`，见 `airlock/runner/sandbox.py`）：工作目录是仓库外新建的临时目录，工具只能碰这个目录，shell 只剩几条只读命令，其他一律拒绝并记录。别在限制模式之外、容器之外用真模型：它读到的东西都会作为工具输出发给模型网关。

CLI 报的 `cost_usd` 是它按自己的价目表估的，续接的会话里还会累加；每一轮的真实用量看账本里的 `usage`（token 数）。

## 部署

- `config.example.yaml`：带注释的完整配置（来源、路由、调查画像、工作画像、订阅、适配器）。密钥只写环境变量名。
- 进程：`python -m airlock.control --config config.yaml`、`python -m airlock.launcher --config config.yaml`、每个调查画像一个 `python -m airlock.runner.investigator`（环境变量配置，见 `airlock/runner/investigator.py` 顶部），出网代理 `python -m airlock.egress.proxy`。
- 操作员密码：`python -m airlock.control.passwd` 生成 scrypt 哈希，放进 `AIRLOCK_OPERATOR_PASSWORD_HASH`。
- `deploy/Dockerfile`、`deploy/compose.yml`：镜像和单机编排的**草图**，四个网络把「谁能连谁」固定成上面的图（调查员连不到启动器）。**没有实际跑过**，上线前要逐条核对。

真正让边界成立的是你要准备的东西，代码替你做不了：

1. 每个调查画像一套**只读**身份（kube RBAC 只给 get/list/watch，IAM 只给 Describe/List/Get）。
2. 每个工作画像一个**专用机器身份**，权限收到它白名单里那几条命令刚好够用，别的都不给；它的永久凭证只放在它自己的 `credentials_dir`。
3. 为每个工作画像写姿态自检，证明容器里拿到的就是那个专用身份。
4. 控制台放在 TLS + 你的 SSO/VPN 后面：它就是批准按钮。

## 挡住什么，挡不住什么

详见 [docs/security.md](docs/security.md)。简单说：调查员被说服了（比如 webhook 里的提示注入），最多写出一份坏计划，而坏计划要过自动校验、你的眼睛、启动器的复核、专用凭证的权限这四道；它挡不住的是**你批准了一份写得很像样的坏计划**，所以计划页把命令、目标、权限、差异都摊开给你看。

## 现状

已实现并有测试（`pytest` 覆盖各模块和一个全链路 e2e；`scripts/demo.py --smoke` 另用真实的多个 HTTP 服务走一遍）：管道进口与出口、路由、调查节点、会诊中转、计划校验与版本、网页控制台、审批绑定、启动器复核、本地运行时、执行器、姿态自检、账本与执行记录的哈希链、出网代理。

真模型跑过的（2026-09-23，经 LiteLLM 用 `gpt-5.6-luna`，Claude Agent SDK 0.2.158 / CLI 2.1.280，受限模式在本机）：`scripts/demo.py --smoke --engine claude` 全流程走通——调查员读证据、经控制面会诊另一个调查员、给出能过校验的计划、按留言修订出新版本、批准后执行；另外单独验证了钩子的拒绝真的挡住 CLI（工作目录外的诱饵文件、`kubectl delete` 都被拒，内容没有到模型那里）。

写了但**没有真跑过**的：

- Docker 运行时：`docker run` 的参数有测试，但没有在 Docker 上跑过一个真容器。
- 容器里的调查员和 task 模式的工作画像（真模型只在本机受限模式下跑过）。
- `deploy/` 下的镜像和编排。

还**没有做**的：

- 用目标系统的原生审计（CloudTrail、k8s audit）对账：专用身份的每一次使用都应能对上一条执行记录，对不上就报警。现在只做了「带上批准编号」这一半。
- 任何具体的适配器（飞书等）：协议有了（签名通知 + `/v1/adapters/<name>/message|decision` + 平台用户映射），适配器本身没写。
- 让批准在密码学上只属于你：现在启动器信任控制面的签名，控制面被攻破就能伪造批准。下一步是用只在你设备上的密钥（WebAuthn）签计划 hash，启动器验这个签名。
- 多操作员、按风险要求二次确认。
